## 1. Sessions

The skeleton uses `mezzio/mezzio-session` (PSR-15 middleware) with `mezzio-session-ext`, i.e. PHP's native sessions. Flash messages are a small class (`App\Http\Flash`) that reads and writes in the session: `Flash::add($session, '…')` in the handler, `flashes()` in the layout. It configures them in `SessionPersistenceFactory`:
- **`save_path` in `app/var/sessions`**: on shared hosting the default folder may be shared among several customers, with session files readable by other scripts on the same server;
- **garbage collection enabled** (`gc_probability=1`, `gc_divisor=100`): some distributions set it to zero and leave cleanup to a system cron, which however does not know about the custom folder. Without GC the files pile up until the inodes run out;
- **cookie** `HttpOnly`, `SameSite=Lax`, `Secure` (if `https` is enabled), custom name;
- **`use_strict_mode`**: PHP rejects session identifiers not generated by the server.

The session is lazy: it is started only if the code reads or writes it, so pages that do not use it send no cookie.

Usage in handlers:
```php
$session = $request->getAttribute(SessionMiddleware::SESSION_ATTRIBUTE);
assert($session instanceof SessionInterface);
$session->set('cart', $items);
$session = $session->regenerate(); // on every privilege change (login, logout)
```

`regenerate()` returns the instance to use: always reassign it. With the `LazySession` provided by the middleware it would work even without doing so, but the `SessionInterface` contract does not guarantee it.

## 2. CSRF

The skeleton's `CsrfMiddleware`:
- generates one token per session (`random_bytes(32)`), valid for the whole session: multiple open tabs do not invalidate each other;
- automatically verifies POST, PUT, PATCH and DELETE, with the `_csrf` field or the `X-CSRF-Token` header for JavaScript requests;
- compares with `hash_equals` and responds 403 if the token does not match;
- runs after the router, so non-existent routes respond 404 and not 403.

In templates: `{{ csrf_field() }}` in every form with `method="post"`.

I chose not to use `mezzio-csrf` for two reasons: it uses single-use tokens with a single key, so a second form open in another tab fails, and it compares with `===` instead of a constant-time comparison.

## 3. Password login

Recommended scheme, session-based and without custom cookies:
```php
// Registration
$hash = password_hash($password, PASSWORD_DEFAULT);

// Login
$user = $users->findByEmail($email);
if ($user === null || !password_verify($password, $user->passwordHash)) {
    // same message for non-existent user and wrong password
    return $this->view->render($request, 'login.html.twig', ['error' => 'Invalid credentials'], 401);
}
if (password_needs_rehash($user->passwordHash, PASSWORD_DEFAULT)) {
    $users->updatePasswordHash($user->id, password_hash($password, PASSWORD_DEFAULT));
}
$session = $session->regenerate();           // new identifier: prevents session fixation
$session->set('user_id', $user->id);
$session->set('auth_version', $user->authVersion);

// Logout
$session->clear();
$session = $session->regenerate();
```
- An authentication middleware for protected routes reads `user_id` from the session, loads the user and compares `auth_version`. By incrementing `auth_version` in the database, for example on password change or with "sign out of all devices", all existing sessions are invalidated.
- If you prefer a signed token in a cookie, for example HMAC over id and expiry, remember that without server-side state (such as `auth_version`) it cannot be revoked before it expires, and that the HMAC secret becomes a critical credential to be protected like the database password.
- `#[\SensitiveParameter]` on parameters that receive passwords.
- Never store the password or the hash in the session.

## 4. File uploads

- Limits in `.user.ini` (`upload_max_filesize`, `post_max_size`), plus an explicit size check in the code.
- PSR-7: `$request->getUploadedFiles()` → `UploadedFileInterface`. Check `getError() === UPLOAD_ERR_OK`.
- Real type from the content: first save to a temporary location, then `finfo_file($path, FILEINFO_MIME_TYPE)` compared against a whitelist.
- Generated name (`bin2hex(random_bytes(16))` + extension from the whitelist), never the name sent by the client.
- **Destination**:
  - private files (documents, attachments) in `app/var/uploads/`, served by a handler that checks permissions and sets `Content-Type` and `Content-Disposition: attachment`;
  - public files (content images) in `assets/uploads/`, where `assets/.htaccess` prevents script execution.
- Do not trust the extension alone: a file `immagine.jpg.php` or a file with PHP content and a `.jpg` name are common attempts.

## 5. Sending email

- The `mail()` function on shared hosting is often restricted, and messages sent this way easily end up in spam due to the lack of consistent SPF/DKIM authentication.
- Use SMTP with the credentials of the mailbox created in the panel, through a library such as `symfony/mailer` or PHPMailer. Host, port, user and password go in `settings.local.php`.
- Port 587 with STARTTLS or 465 with TLS; some hosting providers block outgoing SMTP connections to external servers and allow only their own.
- Bulk sends (notifications, newsletters): put them in a queue table and send them in batches from the cron, respecting the hosting's hourly limits.

## 6. Rate limiting

For login, contact forms and password recovery, without Redis or external services:
- an `attempts (key, attempted_at)` table, where the key is for example the hash of IP and email;
- before processing, count recent attempts (`WHERE key = ? AND attempted_at > ?`); above the threshold respond 429 with `Retry-After`;
- cleanup of old records from the cron;
- take the IP from `REMOTE_ADDR`. Consider `X-Forwarded-For` only if the hosting documents a trusted proxy in front of PHP, otherwise anyone can spoof it.
